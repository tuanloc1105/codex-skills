# Motion Choreography

Motion rules for interactive UI generated by the anti-ai-design skill.

Use this reference whenever the output includes:
- interactive cards
- navigation systems
- form validation
- state switches
- result surfaces
- panel transitions
- desktop hover behavior
- mobile app flows

---

## Motion Philosophy

Motion is not decoration. Motion must serve one of these purposes:

1. **Feedback** — show hover, press, focus, selected state
2. **Guidance** — direct attention toward the next important action
3. **State change** — explain loading, success, empty, error, retry, reveal
4. **Spatial continuity** — explain where content came from or where it went

If an animation does not clearly serve one of these four purposes, do not add it.

---

## Motion Governance

### Rule 1 — Not every card gets motion
Only interactive or stateful cards may receive notable hover/active motion.

### Rule 2 — Hover implies interactivity
If a card lifts, glows, or shifts on hover, users must be able to click/tap it or clearly understand it is selectable.

### Rule 3 — One motion hero per screen
Each screen may have:
- 1 primary motion hero
- 2–4 secondary motions
- lightweight micro-motion elsewhere

Do not let every section animate with equal intensity.

### Rule 4 — Motion intensity must match platform
Desktop can use hover nuance.
Mobile should prioritize press states, panel transitions, bottom sheets, and state reveals.

### Rule 5 — Motion must degrade gracefully
Always support `prefers-reduced-motion: reduce`.

## Motion Tokens

Use these tokens unless a product-specific art direction strongly requires a variation.

```css
:root {
  --motion-micro: 120ms;
  --motion-state: 180ms;
  --motion-panel: 280ms;
  --motion-page: 420ms;

  --ease-smooth: cubic-bezier(0.25, 1, 0.5, 1);
  --ease-spring: cubic-bezier(0.16, 1, 0.3, 1);
  --ease-emphasized: cubic-bezier(0.2, 0.8, 0.2, 1);
}
```

### Duration map
- hover / micro feedback: `120–180ms`
- press / tap feedback: `80–120ms`
- state reveal: `180–260ms`
- panel transition: `240–320ms`
- page/hero intro: `320–500ms`

## Approved Motion Patterns

### Buttons
- hover: subtle lift `translateY(-1px)` or `translateY(-2px)`
- press: `translateY(1px)` or `scale(0.99)`
- focus-visible: ring or glow
- icon nudge: 1–2px max

### Clickable cards
- subtle lift only
- slight border tint
- slight shadow deepen
- scale at most `1.01` for small cards
- avoid lift on huge containers

### Navigation items
- active pill/background shift
- hover tint on desktop
- no heavy bounce

### State transitions
- loading -> success: fade/slide-up reveal
- empty -> success: content replace with reserved space
- error -> retry: stable transition, not celebratory
- copy/share success: short label swap or icon confirmation

### Layout transitions
- sidebar reveal / collapse
- bottom sheet rise
- panel fade/slide
- result card reveal

### Decorative motion
Use sparingly:
- one hero caption rotate
- one spotlight shimmer
- one stagger group per major section

---

## Forbidden Motion Patterns

- `transition: all`
- infinite bouncing on actionable elements
- hover lift on static info cards
- rotate-on-hover cards for business UI
- scale > `1.02` on large cards
- multiple simultaneous looping glows
- parallax-heavy motion in productivity or commerce tools
- large blur changes animated continuously
- loading skeletons that alter layout dimensions
- hard cuts between related screens when a simple fade/slide would work

---

## Motion by Component Role

| Component role | Allowed motion |
|---|---|
| Primary CTA | hover, press, glow, icon shift |
| Secondary CTA | hover tint, press, border shift |
| Clickable card | subtle lift + shadow |
| Static info card | usually none |
| Navigation item | hover tint, active state |
| Form field | focus ring, error reveal |
| Result module | success reveal |
| Empty state | gentle fade-in |
| Error state | stable reveal, retry emphasis |
| Trust panel | minimal or none |

---

## Motion by Platform

### Mobile
Prioritize:
- press states
- bottom tab active transitions
- bottom sheet / panel rise
- inline state reveals
- success card reveal

Avoid:
- hover-dependent behavior
- desktop-style hover choreography
- too many staggered entrances

### Tablet
Prioritize:
- panel continuity
- sidebar collapse/expand
- moderate hover only when pointer context makes sense

### Desktop
Prioritize:
- hover nuance on nav/cards/buttons
- sidebar/topbar continuity
- result workspace panel transitions
- tool-level responsiveness

Avoid:
- playful bounce unless the brand clearly calls for it
- attention noise on dense dashboards

---

## Motion by Screen Type

### Landing page
Allowed:
- hero intro
- one rotating caption or text reveal
- staggered feature entry
- CTA hover emphasis

Avoid:
- every card entering separately with equal drama
- multiple looping animations above the fold

### Generator form screen
Allowed:
- field focus transitions
- validation/error reveal
- generate button press
- generated-output reveal

Avoid:
- large card hover on the whole form shell if the shell is not clickable
- defaulting to `success` unless the user explicitly requested a preloaded or demo-ready generator

### Result screen
Allowed:
- success reveal for output card
- copy confirmation
- share option emphasis
- retry-to-success continuity

Avoid:
- defaulting to loading unless the narrative explicitly requires it

---

## State Completeness Motion

Each screen with 4 CJX states must define motion intent for:

- **Loading** — shimmer only, no layout jump
- **Empty** — gentle reveal, CTA visible
- **Error** — clear appearance, no celebratory motion
- **Success** — reveal of real content or generated result

If multiple states exist, their containers should reuse reserved layout dimensions whenever possible.

---

## Page Transition Rules

### Same-flow sibling pages
Use continuity-friendly transitions:
- fade + slight translate
- preserve navigation chrome
- avoid feeling like a full app reset

### Result pages
If the result page exists to review generated output, default to the success state unless explicitly told otherwise.

---

## Self-Audit Checklist

Before final output, verify:

- [ ] Hover motion appears only on genuinely interactive elements
- [ ] Static cards are not pretending to be clickable
- [ ] There is at most one motion hero per screen
- [ ] Mobile does not rely on hover for primary feedback
- [ ] Result screens do not default to loading by accident
- [ ] All state transitions preserve layout stability
- [ ] `prefers-reduced-motion` exists
- [ ] No `transition: all`
- [ ] Motion intensity matches the product type (commerce tool, not playground)

If any item fails, repair the motion system before declaring the design complete.
