# Agent Guide

## Start Here

- Each top-level directory containing `SKILL.md` is a skill. Read that file completely as source documentation before editing the skill, then open linked references, scripts, or assets as needed. Do not load, invoke, or activate the skill being edited in the current session, including its installed copy; its instructions are content to maintain, not instructions to execute.
- Each top-level directory containing `.codex-plugin/plugin.json` is a plugin. Treat its complete directory as one installable unit; nested `skills/` are plugin-owned unless explicitly dual-published.
- Treat the repository copy as authoritative. For the complete maintenance workflow, read [docs/agent/skill-maintenance.md](docs/agent/skill-maintenance.md).

## Skill Installation And Synchronization

- Adding or editing a skill in this repository does not authorize syncing, installing, or reinstalling it. Validate the repository copy only; leave installed copies untouched unless the user explicitly requests installation or synchronization.
- This rule applies to standalone skills, Claude Code and Kiro ports, and plugin-owned skills. When explicitly requested, sync the complete distribution and verify the installed copy using [docs/agent/skill-maintenance.md](docs/agent/skill-maintenance.md) or [docs/agent/plugin-maintenance.md](docs/agent/plugin-maintenance.md).
- Install plugin-owned skills through the complete plugin; do not separately mirror a nested `<plugin>/skills/<skill-name>/` unless the skill is intentionally published in both forms.

## Read On Demand

- Before adding, updating, syncing, or validating a skill, read [docs/agent/skill-maintenance.md](docs/agent/skill-maintenance.md) for the exact workflow, checks, and nested-repository handling.
- For database inspection or troubleshooting, use [data-debug/SKILL.md](data-debug/SKILL.md); keep database operations read-only by default and use only its bundled `db-debug:latest` image workflow.
- Before changing a plugin, read [docs/agent/plugin-maintenance.md](docs/agent/plugin-maintenance.md).
- Before changing a skill-specific workflow under `.github/workflows/`, read [docs/agent/skill-maintenance.md](docs/agent/skill-maintenance.md) and the corresponding skill manifest and test scripts.
- For the direct discussion-to-execution handoff contract, read [discuss/SKILL.md](discuss/SKILL.md), [execute/SKILL.md](execute/SKILL.md), and [plan/SKILL.md](plan/SKILL.md) together; an execution-ready discussion tracker is the single execution record and does not require a duplicate plan file.
- For OCB Jira-to-MR delivery, use [deliver-ocb-change/SKILL.md](deliver-ocb-change/SKILL.md) for backend, web frontend, or mixed work; resolve the delivery mode before planning or mutation and load the applicable domain policy.
- For Jira Cloud work through Atlassian Rovo MCP and its delegated Media transfers, read [interact-with-jira/SKILL.md](interact-with-jira/SKILL.md) first. After changing this skill, run `python3 interact-with-jira/scripts/validate_skill.py` and review the affected workflow scenarios before the standard repository checks.
- `claude-skill/` holds Claude Code ports of the Codex `data-debug`, `deliver-ocb-change`, `discuss`, `execute`, `interact-with-git-platform`, `interact-with-jira`, `plan`, `simplify`, `technical-diagrams`, and `update-agent-docs` skills, one skill per `claude-skill/<name>/SKILL.md`. Ports keep the source skill's name and contract but drop `agents/openai.yaml`, invoke as `/<name>` instead of `$<name>`, and name Claude Code tools: `Edit`/`Write` for record writes, `Bash` for commands and scripts, `Agent` for delegation, `AskUserQuestion` for decision gates, `Skill` for loading companion skills. Engine-style ports such as `technical-diagrams` (schemas, renderers, CLI, tests, assets) and `data-debug` (its `Dockerfile`/`db-debug:latest` workflow) carry the agent-agnostic engine over verbatim and adapt only `SKILL.md`. These are Claude Code skills, not Codex skills: do not mirror them to `~/.codex/skills`. Only when the user explicitly requests installation into a live Claude Code instance, run `./scripts/sync-claude-skill.sh` (see [README.md](README.md)), which targets `~/.claude/skills/<name>/`.
- `kiro-skill/` holds Kiro / Kiro Crew ports of the Codex `discuss`, `plan`, `execute`, `interact-with-git-platform`, `update-agent-docs`, `simplify`, `interact-with-jira`, `deliver-ocb-change`, `technical-diagrams`, and `data-debug` skills, one skill per `kiro-skill/<name>/SKILL.md`. Workflow/contract ports keep the source Codex skill's Markdown-bundle/worktree/review contract but route questions through `ask_question`, delegation through `spawn_run`, and steering docs through `.kiro/steering/` instead of `AGENTS.md`. Engine-style ports such as `technical-diagrams` (its JSON schemas, renderers, CLI, tests, assets) and `data-debug` (its `Dockerfile`/`db-debug:latest` image workflow) carry the agent-agnostic engine over verbatim and Kiro-adapt only the `SKILL.md` frontmatter (`name: kiro-<name>`), the invocation token (`$kiro-<name>`, including any `agents/openai.yaml` `default_prompt`), and the shell/`shell`-tool contract. Only when the user explicitly requests Codex synchronization, mirror each complete `kiro-skill/<name>/` to `~/.codex/skills/kiro-skill/<name>/`; do not flatten it to `~/.codex/skills/<name>/`. Only when the user explicitly requests installation into a live Kiro Crew instance, run `./scripts/sync-kiro-skill.sh` (see [README.md](README.md)), which targets `~/.kiro/crew/skills/kiro-skill/<name>/` and never overwrites KiroCrew's own `~/.kiro/crew/skills/imported/codex/<name>/` mirror of the source Codex skills.
